\section{Executive Summary \& Business Scenario}

Industrial manufacturing and wholesale distribution enterprises operate in high-volume, multi-role commercial environments. A customer engagement cannot be handled like a generic consumer e-commerce cart. Instead, it must follow an auditable, strict enterprise supply pipeline:

\begin{center}
\begin{tcolorbox}[colback=lightgray,colframe=primary,arc=2mm,width=0.95\textwidth]
\centering
\textbf{Customer Enquiry} $\longrightarrow$ \textbf{Quotation} $\longrightarrow$ \textbf{Sales Order} $\longrightarrow$ \textbf{Inventory Reservation} $\longrightarrow$ \textbf{Dispatch}
\end{tcolorbox}
\end{center}

\subsection{Core Operational Challenges Addressed}
\begin{enumerate}[itemsep=0.3em]
    \item \textbf{Concurrency \& Negative Stock Overselling:} Multiple sales representatives simultaneously confirming high-demand industrial orders for limited stock.
    \item \textbf{Quotation Tampering \& Pricing Discrepancies:} Eliminating client-side calculations so that discount deductions, 18\% GST, and line amounts are strictly governed by backend business rules.
    \item \textbf{Two-Phase Inventory Lifecycle:} Ensuring physical inventory remains un-deducted during the reservation state, while deducting both physical and reserved inventory upon actual warehouse dispatch.
    \item \textbf{Enforced Role-Based Access Control (RBAC):} Guaranteeing via backend middleware that Sales users cannot approve stock reservations or dispatches.
\end{enumerate}

\section{Critical Engineering: Concurrency \& Stock Reservation}

\subsection{The Race Condition Challenge}
Consider a scenario where an industrial product has:
\begin{equation}
\text{Physical Stock} = 120, \quad \text{Reserved Stock} = 20 \implies \text{Available Stock} = 120 - 20 = 100 \text{ units}
\end{equation}
If two sales representatives confirm orders almost simultaneously:
\begin{itemize}[itemsep=0.2em]
    \item \textbf{User A} requests $80$ units.
    \item \textbf{User B} requests $50$ units.
    \item Total demanded = $130$ units, but only $100$ units are available.
\end{itemize}
In standard web applications, both concurrent requests execute parallel \texttt{SELECT} queries, read $\text{Available} = 100$, approve both orders, and set reserved stock to $150$, resulting in a disastrous negative available inventory of $-30$.

\subsection{The Solution: Pessimistic Row-Locking (\texttt{SELECT ... FOR UPDATE})}
The order confirmation engine inside \texttt{salesOrder.controller.ts} wraps the inventory verification and reservation in a strict PostgreSQL database transaction with pessimistic row-locking:

\begin{lstlisting}[language=SQL, caption={Pessimistic Row-Locking Reservation Engine}]
BEGIN;

-- 1. Sort product IDs ascending to eliminate distributed deadlocks
SELECT product_id, physical_qty, reserved_qty 
FROM pern_erp.inventory 
WHERE product_id = ANY($1::int[]) 
ORDER BY product_id ASC 
FOR UPDATE;

-- 2. Verify stock sufficiency inside the exclusive locked boundary:
-- IF (physical_qty - reserved_qty) < requested_qty:
--     ROLLBACK;
--     RAISE EXCEPTION 'INSUFFICIENT_STOCK';

-- 3. Atomically reserve inventory (physical stays constant)
UPDATE pern_erp.inventory 
SET reserved_qty = reserved_qty + $requestedQty, updated_at = NOW() 
WHERE product_id = $productId;

-- 4. Mark Sales Order as CONFIRMED
UPDATE pern_erp.sales_orders 
SET status = 'CONFIRMED' 
WHERE id = $orderId;

COMMIT;
\end{lstlisting}

\subsection{Deadlock Prevention Guarantee}
By sorting all line-item product IDs in strictly ascending order (\texttt{ORDER BY product\_id ASC}) before requesting locks, transactions accessing multiple products acquire locks in the exact same sequence. This mathematically eliminates cycle-wait conditions and prevents PostgreSQL distributed transaction deadlocks.

\subsection{Two-Phase Inventory Deduction Mechanics}
\begin{enumerate}[itemsep=0.3em]
    \item \textbf{At Order Confirmation (Reservation):}
    \begin{equation}
    \text{Physical Quantity} \quad (\text{unchanged}), \quad \text{Reserved Quantity} \uparrow, \quad \text{Available Quantity} \downarrow
    \end{equation}
    \item \textbf{At Physical Dispatch:}
    \begin{equation}
    \text{Physical Quantity} \downarrow, \quad \text{Reserved Quantity} \downarrow, \quad \text{Available Quantity} \quad (\text{unchanged})
    \end{equation}
    \item \textbf{At Order Cancellation:}
    \begin{equation}
    \text{Reserved Quantity} \downarrow \implies \text{Available Quantity} \uparrow \quad (\text{inventory safely released back})
    \end{equation}
\end{enumerate}

\subsection{Server-Side Commercial Pricing Formulation}
Quotation calculations are executed strictly on the server:
\begin{align}
\text{Base Amount} &= \text{Quantity} \times \text{Unit Price} \\
\text{Discount Amount} &= \text{Base Amount} \times \left( \frac{\text{Discount \%}}{100} \right) \\
\text{Taxable Amount} &= \text{Base Amount} - \text{Discount Amount} \\
\text{GST Amount} &= \text{Taxable Amount} \times \left( \frac{\text{GST \%}}{100} \right) \\
\text{Line Amount} &= \text{Taxable Amount} + \text{GST Amount} \\
\text{Grand Total} &= \sum \text{Line Amounts}
\end{align}
